## Integration Check

A cross-phase integration audit was run against the completed milestone (all 6 phases landed,

### BLOCKER found and fixed

**EntityScreen header-to-content vertical gap: 0px, violating POLISH-04.**

`EntityScreen.svelte`'s root `<section>` shipped with no spacing class at all — the one
composition surface in the entire milestone with zero vertical rhythm between its page-header
(`entity-header`) and whatever rendered below it (the error Alert, the loading Skeleton, the
Empty state, or the bounded table Card). Every other composition file in this milestone
(`Shell.svelte`, the create/edit `Dialog` form, `LoginScreen.svelte`) used a `space-y-*` scale at
its own top level; `EntityScreen.svelte` alone did not, leaving `entity-header` flush against its
content — a real, structural violation of POLISH-04's "one consistent scale, no one-off spacing
values" requirement, and directly contrary to the Design Intent section's "consistent rhythm...
page header → content → actions should read as one deliberate flow."

This was a genuine defect, not a nitpick: `cross-phase-verification.spec.ts`'s own spacing
assertions (added in Phase 17 Plan 02) measured row-wise gaps (`gap-2` row actions) and
header-to-header gaps (`columnGap` between Shell's header and each entity's own header) but never
measured the vertical gap *within* a single `EntityScreen` between its header and its content —
exactly the axis this milestone's Design Intent calls out first ("spacing between page header →
content → actions should read as one deliberate flow per screen").

**Fix:** commit `fb52d85` added `class="space-y-6"` to `EntityScreen.svelte`'s root `<section>`,
matching `Shell.svelte`'s own top-level `space-y-6` scale one level down (`Shell.svelte:82`).
Tailwind's `space-y` utility applies this as `margin-block-end` on every child except the last,
so the fix surfaces as a 24px gap on `entity-header` (the section's first, non-last child) against
whatever renders next — on-scale with every other page-level rhythm value in the milestone.

**Re-verification, this session:** the original proof of `fb52d85` was a throwaway scratch spec
that was deleted after confirming the fix, leaving no permanent regression coverage — exactly the
kind of fix-without-a-lasting-test gap this audit exists to catch. This session closed that gap by
adding a permanent test, `POLISH-04: entity-header to content vertical gap is non-zero and on the
space-y-6 scale`, to `web/e2e/cross-phase-verification.spec.ts` — it measures the gap via
`getComputedStyle(entityHeader).marginBlockEnd` (asserting `24px`, not `0px`) and corroborates
with the actual rendered bounding-box delta between `entity-header` and `entity-table-frame`
(asserting it is strictly greater than zero, not just that the CSS property exists in isolation).
The full Playwright suite was re-run live in full: **69 passed, 0 failed, 0 skipped** (up from 68
before this test existed), zero regression across all 9 entities and all 3 capability classes
(full-CRUD, restricted, read-only). `bun run check` and `bun run lint` both remain at the same
v1.1-established baseline (1 pre-existing warning, 1 pre-existing info; zero new suppressions).

**This BLOCKER does not block milestone completion.** It was found, fixed, and re-verified with
permanent coverage within the same milestone-closing pass — the defect never shipped without a
fix, and the fix now has lasting proof rather than a deleted scratch spec.

### WARNINGS found (non-blocking, informational)

**1. `App.svelte`'s retained `<h1>Apollo v2</h1>` inside the `<SignedOut>` branch.**

`App.svelte` renders a root `<h1>Apollo v2</h1>` immediately above `<LoginScreen />` when signed
out. At first glance this looks like the same "stray root `<h1>`" SHELL-01 explicitly targeted and
removed from `Shell.svelte` — but it is a structurally different element in a structurally
different branch: SHELL-01's scope was `Shell.svelte`'s own authenticated chrome (replacing the
floating logout button and stray heading with a proper header/toolbar row), not the unauthenticated
`App.svelte` root. This `<h1>` is retained intentionally — `LoginScreen`'s own restyled `Card`
(Phase 12) visually supersedes it in the rendered layout, and `shell-chrome.spec.ts`'s "single
app-identity element when authenticated" test explicitly proves exactly one root `<h1>` exists
*when authenticated* (Shell's own), which this pre-existing, pre-authentication `<h1>` does not
contradict — it is obscured/redundant in the signed-out view, not a duplicate SHELL-01 defect, and
is exercised (rendered, not orphaned markup) by every login-flow-related test in the suite. Not a
defect; flagged here only for visibility since it reads similarly to the fixed SHELL-01 pattern at
a glance.

**2. Shell nav's `flex-wrap` strategy has no explicit single-row assertion.**

`Shell.svelte:85` uses `<nav class="flex flex-wrap gap-2">` for the 9-item entity nav (SHELL-02).
`shell-chrome.spec.ts`'s "nav overflow strategy" test proves the strategy is a single flat
wrapping row (not `Tabs`, not a scroll container) and that all 9 buttons are present and
reachable, but at today's desktop viewport widths this milestone tests against, the row happens to
never actually wrap onto a second visual line — no test asserts that it stays single-row at the
specific viewport width used, only that the CSS strategy itself (`flex-wrap`, not `overflow-x-auto`
or similar) is the one in place. Functionally this is fine today: all 9 nav items are visible,
clickable, and keyboard-reachable in every test run, and `flex-wrap` is explicitly the deliberate,
documented SHELL-02 strategy (not an accidental omission). This is flagged purely as a minor
coverage gap — a future viewport-width or nav-item-count change could cause an actual visual wrap
with no automated check watching for it — worth a small follow-up assertion in a future milestone,
not a defect in what v1.2 shipped.

## Non-Blocking Tech Debt Carried Forward

Logged in `STATE.md`'s Accumulated Context / Blockers-Concerns section, confirmed still accurate
and unfixed as of this audit:

1. **Phase 16 WR-01** — no type-level invariant enforces that any entity with
   `capabilities.delete: true` also has `capabilities.create: true`. `EntityScreen.svelte`'s
   post-delete focus fallback targets `entity-create-start`, which would silently no-op if a
   future entity ever broke that pairing. All 9 current entities satisfy it today; not a live bug.
2. **Phase 16 WR-03** — a hung `db.transact` during delete leaves the delete-confirmation
   `AlertDialog` permanently undismissable, with no timeout/abort path. Same class of edge case as
   any other in-flight-write UI in this app; not new to this phase, not unique to delete.
3. **Phase 17 WR-01** (test-quality only) — the `fundos` keyboard/focus-visible smoke test in
   `cross-phase-verification.spec.ts` assumes the newly created row is the first Tab stop, with no
   assertion that the table has exactly one row — a fragile, unasserted invariant on a live shared
   table, not a production defect.
4. **Phase 17 WR-02** (test-quality only) — four cleanup helpers in `cross-phase-verification.spec.ts`
   swallow all errors indiscriminately in their "already deleted, fine" `catch` blocks, which could
   mask a genuine delete-path regression rather than only the expected already-gone case.

None of these four items affect any shipped user-facing behavior; all are scoped, documented, and
recommended for review in a future milestone rather than blocking this one.
