<objective>
Convert `EntityScreen.svelte`'s row-level delete confirmation from native `window.confirm()` to a shadcn
`AlertDialog` (DELCONF-01), and fix row action button (`row-edit`/`row-delete`) alignment/spacing (ENTTBL-08)
— for all 9 entities across all 3 capability classes, since `EntityScreen.svelte` is the one generic
component every entity shares, and this is the highest-risk sub-step in the v1.2 milestone per research
(portal/focus-management regressions). This plan does the actual conversion, proves the cancel and confirm
paths plus their focus-management behavior end-to-end against `fundos` (the tracer entity), and migrates the
one pre-existing spec file (`entities-fundos.spec.ts`) whose delete step this conversion breaks. Plan 16-02
(wave 2) migrates the remaining 4 affected spec files, adds dedicated keyboard/focus/alignment coverage, and
runs the full-suite regression.

Purpose: `window.confirm()` was explicitly logged as v1.1 tech debt and is now in scope as its own reviewed
sub-scope (per CONTEXT.md/ROADMAP.md), not folded silently into a spacing diff. Row actions stay non-portaled,
inline `Button`s — no `DropdownMenu`/kebab menu — per the explicit, already-established decision in
CONTEXT.md and PROJECT.md's Out of Scope table.
Output: `EntityScreen.svelte`'s row-action markup and delete flow restructured in place; the `AlertDialog`
primitive vendored via `bunx shadcn-svelte add`; `web/e2e/helpers/delete-confirmation.ts` (new); one migrated
spec file (`entities-fundos.spec.ts`) proving both the cancel and confirm paths, with empirical focus checks.

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (client) → InstantDB hosted backend (`db.transact` via `confirmDelete`) | Pre-existing destructive write path, now gated behind an explicit `AlertDialog` confirm step instead of `window.confirm()` — identical payload (`tx[config.etype][row.id].delete()`), identical error/toast handling; only the confirmation mechanism changes. |
| User (keyboard/mouse) → AlertDialog confirm/cancel decision | The one genuinely new interaction surface this phase introduces — a single click/keypress irreversibly deletes a real record once confirmed, same end effect as `window.confirm()` had, but with richer focus/keyboard semantics that must not make an accidental confirm easier than the native dialog did. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Tampering | `confirmDelete`'s re-entrancy | medium | mitigate | `deleteBusy` guard (`if (!pendingDelete \|\| deleteBusy) return;`) plus `disabled={deleteBusy}` on both `AlertDialog.Action`/`Cancel` blocks a second concurrent delete call, mirroring `handleSubmit`'s existing `busy` re-entrancy pattern. |
