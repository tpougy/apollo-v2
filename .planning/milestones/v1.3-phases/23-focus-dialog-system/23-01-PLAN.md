architectural problem surfaces on this plan's own commit rather than after 6 more dialogs have

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `dialogStack`'s `id` -> `ticketRows().find(...)` lookup | Client-side only; never an authorization check -- the real boundary is `instant.perms.ts`'s unchanged `donoId`-scoped `view` rule already applied server-side to `DASHBOARD_QUERY` |
| `ticket.corpo`/`remetente` (user-authored email content) -> DOM | Rendered via plain Svelte `{value}` interpolation only, never `{@html}` |
| "editar" hidden host -> `db.transact` | Delegates 100% to `EntityScreen.svelte`'s existing, unmodified `handleSubmit`; this plan adds no new write path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-01 | Information Disclosure | `dialogStack` id resolving to a row absent from the user's own `ticketRows()` (e.g. a manipulated `data-eid`) | low | accept | Server-side `donoId` scoping means such an id can never resolve to another user's data client-side in the first place -- `activeTicket` simply evaluates `undefined` and `TicketDialog`'s `{#if ticket}` guard renders nothing, never a crash or a leak |
| T-23-02 | Tampering | Rendering `ticket.corpo`/`remetente` (free-text, user/email-authored) in the dialog body | low | mitigate | Svelte's default `{value}` text interpolation auto-escapes; this plan uses no `{@html}` anywhere in `TicketDialog.svelte` |
| T-23-03 | Elevation of Privilege | A future dialog treating `dialogStack`/its id-based lookup as an authorization boundary | low | mitigate | Documented explicitly in this plan's SUMMARY and repeated in every later dialog plan's own threat model: the real boundary is always `instant.perms.ts`'s server-side `donoId` scoping, mirroring `SubtarefasPanel.svelte:44-47`'s own precedent |
</threat_model>
