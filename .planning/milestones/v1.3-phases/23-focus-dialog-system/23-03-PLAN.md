`projetos-section.spec.ts` tests that already depend on those elements' current click behavior.
Output: `TaskDialog.svelte`, `EtapaDialog.svelte`, `ProjetosSection.svelte`'s wired kanban AND list

self-contained shape (Plan 23-01: own hidden edit host, own ver-pagina function, `breadcrumb` prop
present but consumed only by later plans). Declare
`TaskDialogRow = { id: string; titulo: string; descricao?: string | null; tipoPrazo: string; dataPrevista?: string | null; dataPrevistaEstimada?: string | null; competencia?: string | null; status: string; subtarefas?: { id: string; titulo: string; concluida: boolean }[]; etapaNome?: string | null; projetoNome?: string | null; fundoNome?: string | null }`.
This flat, pre-shaped-by-the-host contract (rather than a nested `etapa.projeto.fundo` link chain)
is deliberate: every host that resolves a tarefa (`ProjetosSection.svelte` here; `Dashboard.svelte`
in Plans 23-04/23-06) has a DIFFERENT raw query shape, so each host does its own join/resolution
(per `<threat_model>`'s trust-boundary note and `derive.ts`'s own established
"cross-referencing happens once, at the host" discipline) and hands this dialog a flat,
already-resolved row -- `TaskDialog.svelte` itself never inspects a nested link.

Props: `open: boolean`, `tarefa: TaskDialogRow | undefined`, `onOpenChange: (open: boolean) => void`,
`breadcrumb?: { label: string; onClick: () => void }`. Resolve `tarefasConfig` via `requireConfig`
(the `configByEtype` idiom). Content (spec §4 row 3 "conteúdo mínimo": campos da tarefa, etapa e
projeto pai ou "Sem etapa", prazo, competência, subtarefas): title = `tarefa.titulo`; contexto =
`` `${tarefa.fundoNome ?? "Sem fundo"} · ${tarefa.etapaNome ? `${tarefa.projetoNome} · ${tarefa.etapaNome}` : "Sem etapa"}` ``.
Body: `descricao` (if present), a line combining `tipoPrazo.toUpperCase()` + formatted
`dataPrevista` (apply `text-destructive` when overdue -- import `vencido`/`tarefaConcluida` from
`../derive` and compute `vencido(tarefa.dataPrevista, tarefaConcluida(tarefa), new Date())`; note
`tarefaConcluida` needs the full `TarefaLike` shape, so pass `{ subtarefas: tarefa.subtarefas }`),
`dataPrevistaEstimada` (if present), `competencia` (if present), `status`; then a
`data-testid="task-dialog-subtarefas"` read-only list of `tarefa.subtarefas ?? []` (title +
disabled `Checkbox`, no click handler -- Tarefa is always a leaf per depth-cap-2, whether reached
directly or as a second-level dialog). "editar" drives `tarefasConfig`'s own hidden host
(`task-dialog-edit-host` testid) exactly like `TicketDialog.svelte`'s pattern. "ver na página
completa" clicks `[data-testid="nav-projetos"]` then calls `onOpenChange(false)` (per
23-RESEARCH.md Q3's table row 3). `size="S"`.

Create `web/src/lib/dashboard/dialogs/EtapaDialog.svelte`, identical shape. Declare
`EtapaDialogRow = { id: string; nome: string; ordem: number; projetoNome?: string | null; fundoNome?: string | null; tarefas?: { id: string; titulo: string; dataPrevista?: string | null; status: string; subtarefas?: { concluida: boolean }[] }[] }`.
Props: `open: boolean`, `etapa: EtapaDialogRow | undefined`, `onOpenChange`, `breadcrumb?`. Content
(spec §4 row 6: todas as tarefas da etapa sem o limite de 3, ordem, projeto pai): title =
`etapa.nome`; contexto = `` `${etapa.fundoNome ?? "Sem fundo"} · ${etapa.projetoNome ?? "Sem projeto"}` ``.
Body: the `ordem` value, then a `data-testid="etapa-dialog-tarefas"` list of EVERY tarefa in
`etapa.tarefas ?? []` (no 3-item cap, unlike the Dashboard's own mini-kanban strips), each a plain
read-only row (title, prazo formatted + `text-destructive` when overdue via `vencido`, `status`) --
NOT a button; Etapa is always a leaf (its own task list never opens a Tarefa dialog from inside
the Etapa dialog -- that click target only exists one level up, in the Projeto dialog's own kanban
body, per resolved decision on depth-cap-2). "editar" drives `etapasConfig`'s own hidden host
(`etapa-dialog-edit-host`). "ver na página completa" clicks `nav-projetos`. `size="M"`.
