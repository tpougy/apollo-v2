<objective>
Give `apollo rotina gerar-instancias` explicit control over its generation window: `--competencia AAAA-MM` or `--de`/`--ate` REPLACE the default `[today (or --data-base), end_of_next_month]` range entirely, so an operator can generate exactly one competencia without dragging the following month along (ROADMAP Success Criterion 1), and can recover already-passed dates of the current month when running mid-month (Success Criterion 2) — both proven live against the real production InstantDB app, alongside a live idempotency proof that a recorte and a wider/absent recorte covering the same window always produce the identical instance set (Success Criteria 3/4).

This is the phase's tracer: Task 1 wires the CLI flags all the way through `_resolve_range_override` -> `run_routine_instance_job` -> `compute_expected_instances` -> real InstantDB writes, end-to-end, for the exact two named real-world scenarios from ROADMAP.md ("gerar só agosto sem arrastar setembro" / "recuperar instâncias já passadas do mês corrente rodando no meio do mês"). Task 2 completes cross-runtime parity (C-06) by mirroring the pure-compute-core generalization (`months_in_range`/`monthsInRange`) into `web/src/lib/routineJob.ts` and the shared fixture, even though no SPA surface exists for this command (D-07/D-08).

Purpose: today `compute_expected_instances`/`computeExpectedInstances` always compute `range_start = today`, `range_end = end_of_next_month(today)` with zero way to narrow it — a real operational gap when running the job in volume (REQUIREMENTS.md RANGE-01).
Output: `--competencia`/`--de`/`--ate` on `gerar-instancias`, `months_in_range`/`monthsInRange` as the byte-compatible generalization of `_compute_fixed_instances`'s old `today`-derived `candidate_months`, and cross-runtime fixture coverage proving both runtimes agree and that the old behavior is unchanged when no recorte is given.
</objective>

## Scope deviation from PATTERNS.md Analog B (deliberate, read before Task 1)

29-PATTERNS.md's Pattern Assignment #3 Analog B suggests placing the new `--competencia`
format-validation callback "next to `validate_iso_date` in `crud_helpers.py`" (shared plumbing).
29-CONTEXT.md's decision D-07 LOCKS this phase's scope to exactly four files:
`cli/apollo_cli/routine_job.py`, `web/src/lib/routineJob.ts`, `cli/apollo_cli/entities/rotina.py`
("só os novos flags de gerar-instancias e seu --help"), and `shared/routine-job.testcases.json` —
`crud_helpers.py` is NOT in that list. This plan honors the LOCKED decision over the pattern
suggestion: `_validate_competencia_format` and `_resolve_range_override` are both new PRIVATE,
rotina.py-local functions (never exported, never added to `crud_helpers.py`) — they are part of
implementing "os novos flags de gerar-instancias," which decision D-07 does authorize. `--de`/
`--ate` still reuse `crud_helpers.validate_iso_date` verbatim (already imported, D-05) — only the
NEW `AAAA-MM`-format callback stays local to rotina.py. Similarly, resolving `--competencia`'s
month-end reuses Python's stdlib `calendar.monthrange` directly (the exact same one-line idiom
`routine_job.py`'s private `_last_day_of_month` already wraps) rather than importing that
underscore-prefixed function across a module boundary — no custom day-counting logic is
duplicated, only the same stdlib call.
