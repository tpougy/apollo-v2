<objective>
Close the one real (non-crash-risk) parity gap RESEARCH.md's Open Question 1 identified:
`web/src/lib/entities/defs/templatesRotina.ts` hard-codes `tipoGeracao`'s SPA select to the
three pre-existing options and has no `diaSemana` field at all. This plan extends both, so a
`semanal` template is a first-class, selectable option from the SPA — not just something the
CLI can write and the SPA can only display as raw text — mirroring PROJECT.md's core value
("the user can execute every piece of controladoria data-entry work from either the Svelte SPA
or the Python CLI") and Phase 5's own precedent (05-01 Task 3 did the identical thing for
`offsetDias` in the same phase it added the field to the CLI).

Purpose: without this, a `semanal` template created via the CLI (Plan 28-02) would open in the
SPA edit form with `tipoGeracao`'s dropdown showing no matching selected option (cosmetic, not a
crash — `EntityScreen.svelte` already renders an out-of-options stored value as plain text) and
no way to set `diaSemana` from the SPA at all.
Output: `tipoGeracao`'s SPA select offers `"semanal"` as a real option, a new `diaSemana` select
field exists on the form (7 weekday tokens, `required: false`), `listColumns` surfaces it, and
the two pre-existing e2e specs asserting `tipoGeracao`'s exact option set are repaired to match.
</objective>
