<objective>
Close the schema gap that blocks the entire phase: `templatesRotina` has no field to store
WHICH weekday a `tipoGeracao = "semanal"` template targets. Add exactly one optional string
attribute, `diaSemana`, and push it live before any CLI/compute code in Plan 28-02/28-03 tries
to read or write it.

**Storage decision (RESEARCH.md, supersedes CONTEXT.md's tentative lean):** a NEW field
`diaSemana: i.string().optional()`, NOT a reuse of the existing numeric `offsetDias` field.
CONTEXT.md's premise that this would be "the first schema migration since v1.0" is factually
wrong — `offsetDias` itself was added via exactly this push playbook in Phase 5
(commit `81155ed`, `.planning/milestones/v1.0-phases/05-idempotent-routine-instance-job/05-01-PLAN.md`).
Every other choice-shaped field in this schema (`tipoGeracao`, `regraCompetencia`, `status`) is
a plain string, never an encoded integer — reusing the numeric `offsetDias` for a weekday name
would be the first violation of that convention, not a continuation of one.

Purpose: without a live, writable `diaSemana`, Plan 28-02's compute/CLI work has nothing to
read from, and `instant.perms.ts`'s `attrs.allow.create: "false"` will reject any write
attempting to set an attribute the live app doesn't yet recognize.
Output: `diaSemana` live in the real InstantDB app (the one holding 18 fundos/84
templatesRotina/168 instanciasRotina from the real onboarding), proven via a server-side pull,
with regression proof that every pre-existing attribute survived untouched.
</objective>
