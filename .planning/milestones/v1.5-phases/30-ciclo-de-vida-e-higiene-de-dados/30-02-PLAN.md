## Engineering decisions this plan makes (D-06's required "document explicitly why")

**Decision A — where the new dedupeKey-prefix sweep logic lives.** CONTEXT.md decision 5b asks
this plan to confirm whether a bare `apollo rotina instancia deletar` CLI command already exists or
needs adding, purely for test cleanup (explicitly NOT the C-06-forbidden production escape hatch).
Direct reads this session found something CONTEXT.md/30-PATTERNS.md's analog search did not: an
ALREADY-ESTABLISHED, test-only admin-API escape hatch exists exactly for this class of problem —
`web/e2e/fixtures/instancia-admin-fixture.ts`'s `listInstancesByTemplate`/`deleteInstancesByTemplate`
pair (already used live by `routine-job.spec.ts`), plus `deleteAdminRecord`'s own doc comment
explicitly naming this pattern "TEST-CLEANUP-ONLY escape hatch" for entities with no delete path by
design. This plan extends THAT file with one new function (`sweepInstancesByDedupeKeyPrefix`)
instead of adding a bare `instancia deletar` CLI command: it requires zero change to
`rotina.py`'s C-06-protected command surface or its module docstring's production narrative, this
fixture file is grep-confirmed never imported from `web/src` (never bundled into the shipped app),
and it mirrors an already-proven, already-live pattern rather than inventing a new one. No bare
`instancia deletar` CLI command is added by this phase.

**Decision B — do NOT centralize the pre-existing `tryDelete`/`tryDeleteTemplate` wrapper
functions.** 30-PATTERNS.md notes centralizing today is "roughly a wash file-count-wise." This plan
makes the narrower, lower-risk call: leave each file's own `tryDelete`/`tryDeleteTemplate`
definition in place (only its OWN body changes, 1-3 lines, to conditionally append `--force` — see
Task 1/2 actions below), rather than extracting a shared `web/e2e/helpers/sweep.ts` that would
require rewriting every one of the ~40 existing call sites' import structure across 8 files for a
behavior that is already correct and does not need duplication removed. The genuinely NEW logic
(dedupeKey-prefix instance sweep, decision 5b) is a different story: writing that 8 times would
risk exactly the kind of per-file inconsistency that produced the original incident, so THAT piece
is centralized into one shared fixture function (Decision A above) that every file that needs it
imports and calls identically.

**Decision C — which files need the new instance sweep, and which need only the `--force` fix.**
Grep-confirmed this session: only 5 of the 8 files ever seed an `instanciasRotina` row with a
`PREFIX`-tagged `dedupeKey` via `seedInstance` (`dashboard.spec.ts`, `focus-dialog-button-inventory.spec.ts`,
`focus-dialog-dia-rotina.spec.ts`, `focus-dialog-fundo.spec.ts`, `entities-rotina-log.spec.ts`) — these
5 gain BOTH fixes. The other 3 (`routine-job.spec.ts`, `routine-job-cross-channel.spec.ts`,
`entities-form-restyle.spec.ts`) only ever create job-generated instances (whose `dedupeKey` is
`templateId:competencia:dataPrevista`, never `PREFIX`-tagged, so a prefix-based sweep would always
be a no-op for them) or never touch `instanciasRotina` at all — these 3 gain ONLY the `--force`
fix, avoiding dead-code additions that would earn no coverage.
