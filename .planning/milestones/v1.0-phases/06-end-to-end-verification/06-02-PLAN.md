<scope_notes>
**What "mid-generation" can and cannot mean here (RESEARCH Pitfall 2 — read before writing any assertion).** The InstantDB Python SDK's `transact()` issues exactly ONE HTTP POST to `/admin/transact` carrying every step (verified against `cli/.venv/lib/python3.12/site-packages/instantdb/_sync/client.py`), and InstantDB's transact API is atomic. A single `apollo rotina gerar-instancias` invocation therefore CANNOT produce a torn write where some of that run's new `instanciasRotina` exist and others do not. The only two reachable post-kill states are **zero** of that run's new records or **all** of them.

This makes the correct assertion `post_kill_count in (0, len(expected_new))` — and an assertion of the form `0 < count < expected` is a FAILURE signal (the atomicity guarantee broke), never a success case. Do not write a test that "expects" a partial state.

**Scope: CLI only** (RESEARCH Open Question 2). VERIFY-04 is proven against the `apollo rotina gerar-instancias` process, where an OS-level `SIGKILL` is a genuine unclean interruption. A browser-tab-close against `web/src/lib/routineJob.ts` is deliberately NOT in scope: 06-CONTEXT.md frames VERIFY-04 exclusively as spawning the CLI as a subprocess, and the SPA has no equivalent "did the in-flight fetch already leave the process" boundary that a kill can be aimed at. This narrowing is recorded here explicitly so it is not a silent scope reduction — the SPA's non-duplication under concurrency is already proven by Phase 5's `routine-job.spec.ts` double-run and `test_routine_job_parity.py`'s concurrent-process proof.

**`SIGKILL`, never `SIGTERM`.** `SIGTERM` lets Python run `finally`/`atexit` handlers, which would mask exactly the unclean-interruption scenario the requirement describes.
</scope_notes>
