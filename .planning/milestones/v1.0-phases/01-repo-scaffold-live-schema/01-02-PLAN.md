<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo root `.env.instantdb` → `cli/` process memory | The file holds `INSTANT_APP_ADMIN_TOKEN`, which bypasses every InstantDB permission rule |
| `apollo` CLI stdout/stderr → terminal, logs, SUMMARY files | Anything printed can be captured into a tracked artifact |
| `cli/` process → InstantDB (Phase 3 onward) | Must act as a permission-scoped real user, never as admin |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05b | Spoofing / Elevation of Privilege | `cli/apollo_cli/config.py` | high | mitigate | `InstantConfig` carries `admin_token_present: bool` and deliberately has no field for the token value. The key name appears only in the presence check in `config.py`; gate asserts `grep -c 'INSTANT_APP_ADMIN_TOKEN' cli/apollo_cli/cli.py` equals 0. This keeps Phase 3's auth work from taking the admin shortcut by accident. |
| T-01-08 | Information Disclosure | `apollo doctor` output | medium | mitigate | `doctor` prints only the last 4 characters of the app id and a boolean for the token. Gate asserts neither full literal value appears in its output — important because SUMMARY files and autonomous-run logs capture CLI output verbatim. |
| T-01-09 | Information Disclosure | `python-dotenv` usage | medium | mitigate | Use `dotenv_values()` (returns a mapping) rather than `load_dotenv()` (mutates `os.environ`), so the admin token never enters the process environment where a subprocess or a crash dump could pick it up. |
| T-01-10 | Tampering | pre-1.0 `ty` / young `instantdb` dependency drift | low | mitigate | Both are pinned with upper bounds in `cli/pyproject.toml` and locked in `cli/uv.lock`, so a patch release cannot silently change gate behaviour mid-milestone. |
