Public API — TypeScript (`web/src/lib/bizdays.ts`):

    export const CALENDAR_START: string;   // "2000-01-01", read from the JSON's `start`
    export const CALENDAR_END: string;     // "2078-12-25", read from the JSON's `end`
    export class InvalidDateError extends Error {}     // name === "InvalidDateError"
    export class CalendarRangeError extends Error {}   // name === "CalendarRangeError"
    export function isBusinessDay(date: string): boolean;
    export function addBusinessDays(date: string, n: number): string;
    export function nextBusinessDay(date: string): string;

Public API — Python (`cli/apollo_cli/bizdays.py`):

    CALENDAR_START: Final[str]
    CALENDAR_END: Final[str]
    class InvalidDateError(ValueError): ...
    class CalendarRangeError(ValueError): ...
    def is_business_day(date: str) -> bool: ...
    def add_business_days(date: str, n: int) -> str: ...
    def next_business_day(date: str) -> str: ...

Shared reference algorithm (both sides implement this exactly):

1. `parse(date)`: reject anything that is not a `str`/`string` -> `InvalidDateError`. Reject anything not matching `^\d{4}-\d{2}-\d{2}$` -> `InvalidDateError`. Reject a syntactically valid but non-existent calendar date (e.g. `2001-02-29`, `2000-13-01`) -> `InvalidDateError`. Python: `datetime.date.fromisoformat` inside try/except after the regex check. TypeScript: build with `Date.UTC(y, m-1, d)` and reject if the round-tripped year/month/day do not equal the inputs.
2. `assertInRange(iso)`: `CALENDAR_START <= iso <= CALENDAR_END` (plain lexicographic string comparison is correct for zero-padded ISO) else `CalendarRangeError` whose message names the offending date and the valid window.
3. `isBusinessDay(date)`: parse, assertInRange, then return "not Saturday, not Sunday, not in the holiday set". TypeScript uses `getUTCDay()` (0 = Sunday, 6 = Saturday) against a `ReadonlySet<string>` built once at module load. Python asks the `bizdays.Calendar` built from the vendored holidays (see below).
4. `addBusinessDays(date, n)`: parse, assertInRange. If `n === 0`, return the input ISO string unchanged — no adjustment even if the input is a weekend/holiday. Otherwise `step = n > 0 ? 1 : -1`, `remaining = abs(n)`; loop: advance one calendar day by `step`, assertInRange on the new day (so walking off the calendar raises `CalendarRangeError`), and if that day is a business day decrement `remaining`; stop at `remaining === 0`; return the ISO string.
5. `nextBusinessDay(date)`: return `addBusinessDays(date, 1)`. This is **strictly-after** semantics — a date that is already a business day still advances. It is deliberately NOT `bizdays`' `Calendar.following()` same-day-passthrough behavior.

Python calendar construction — the ONLY correct form:

    from bizdays import Calendar
    cal = Calendar(holidays=payload["holidays"], weekdays=["Saturday", "Sunday"])

FORBIDDEN: `Calendar.load("ANBIMA")` anywhere in shipped code. It sources holidays from the library's own bundled table instead of the vendored JSON, violating CAL-03 and guaranteeing silent drift on any future `bizdays` upgrade.

Fixture shape (`shared/bizdays.testcases.json`) — a JSON array; each element has:

    { "id": "<stable unique slug>", "op": "isBusinessDay" | "addBusinessDays" | "nextBusinessDay",
      "date": "<input string, may be intentionally malformed>",
      "n": <int, required iff op === "addBusinessDays">,
      "expected": <bool for isBusinessDay | "YYYY-MM-DD" for the other two>   // present iff no error
      "error": "InvalidDateError" | "CalendarRangeError"                     // present iff no expected
    }

Exactly one of `expected` / `error` is present per case. Both consumers MUST fail the suite on an unrecognized `op` and on a case that has neither or both keys — an unhandled case must never silently pass.
