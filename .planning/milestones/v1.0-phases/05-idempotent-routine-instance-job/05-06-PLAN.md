  <behavior>
    - Two `apollo rotina gerar-instancias` processes launched concurrently against the same fresh template set leave exactly the expected number of instances — never more.
    - No dedupeKey appears on two distinct records.
    - Neither process leaves the app in a state where an instance is missing (the union of both runs' work is complete).
    - At least one process may report keys under `existing` rather than `created` — either split is acceptable, but their union must equal the full expected key set.
    - Neither process exits with an unhandled traceback; a lost race surfaces as a normal JSON report, not a crash.
  </behavior>
  <action>
    Add a live, concurrency-marked test to `cli/tests/test_routine_job_parity.py` that seeds
    a fresh `phase05-conc-` template set, then launches TWO real `apollo rotina gerar-instancias`
    processes with `concurrent.futures.ThreadPoolExecutor(max_workers=2)` over
    `subprocess.run` (real processes, not in-process `CliRunner` calls — `CliRunner` would
    serialize on the same interpreter and could share client state, making the test a
    sequential run wearing a concurrency costume).

    Submit both futures before collecting either result so their query→diff→transact windows
    genuinely overlap. Do NOT add a stagger, a lock, or a retry loop around them: the entire
    point is to force the interleaving that the app-level diff cannot prevent and that only
    `dedupeKey.unique()` can.

    Assert: both processes exit 0; each emits one parseable JSON document; the union of both
    reports' `created` + `existing` key sets equals the full expected key set with no key
    appearing as `created` twice; a live query shows each dedupeKey exactly once; and the
    total instance count equals the expected count.

    Add a companion assertion that reads the LIVE schema, not the local file, to prove the
    constraint the test depends on is actually in force: run `bun run instant:verify` from
    `web/` (or assert it was run by `verify-phase-05.sh`) and grep the pulled schema for
    `dedupeKey` carrying `unique`. If the constraint were ever dropped, this test would still
    likely pass by luck on a fast machine — pinning the constraint separately is what makes
    the proof honest rather than probabilistic.

    Clean up every created template and instance in teardown.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two concurrent writers → one dedupeKey | No coordination exists between a browser tab and a CLI process, or between two tabs |
| verification script → live app | The script creates and must delete real records in the single production app |
| documentation → operator expectations | A guarantee documented but untested becomes a false assurance an operator will rely on |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-05-34 | Tampering | Cross-channel key mismatch producing shadow duplicates | mitigate | Task 1 Test 2 asserts the CLI reports the SPA's exact dedupeKeys under `existing`, proving recognition rather than coincidental non-writing |
