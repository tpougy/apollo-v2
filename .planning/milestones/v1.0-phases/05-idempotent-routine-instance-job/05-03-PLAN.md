## Orchestration specification

1. **Read templates.** `db.queryOnce({ templatesRotina: { $: { where: { ativo: true, donoId } } } })`.
   If zero rows → return `{ created: [], existing: [], skipped: [] }` immediately.
2. **Read existing instances for those templates.**
   `db.queryOnce({ instanciasRotina: { template: {}, $: { where: { "template.id": { $in: templateIds } } } } })`.
   Never issue this query with an empty `templateIds` array — step 1's short-circuit
   guarantees that (RESEARCH Pitfall 5; `$in: []` semantics are unverified and must not
   be relied on). Map each row to the `ExistingInstance` shape from 05-02, taking
   `templateId` from the nested `template` selection.
   **Date normalization is mandatory:** `dataPrevista` is an `i.date()` attribute and
   round-trips from InstantDB as an ISO *datetime* string, not `YYYY-MM-DD` (proven by
   `cli/tests/test_rotina_instancia.py`, which asserts with `.startswith(...)`, not `==`).
   Normalize every DB-sourced date with a leading-10-character slice before it touches
   compute or any comparison. A missed normalization here silently makes every existing
   instance look "new" and duplicates the entire table.
3. **Compute.** `computeExpectedInstances(templates, today, existing)` — pure, from 05-02.
4. **Diff.** `existingKeys = new Set(existing.map(e => e.dedupeKey))`;
   `toCreate = expected.filter(e => !existingKeys.has(e.dedupeKey))`.
   If `toCreate` is empty → return the report with everything in `existing`, issuing
   **no transact at all**. This is the idempotent no-op path and the mechanism that
   makes the status-preservation guarantee structural rather than incidental: an
   already-present dedupeKey is never included in any write payload, so there is no code
   path through which `status` can be overwritten (RESEARCH Pitfall 1).
5. **Write.** One `db.transact` with one chunk per `toCreate` entry:
   `db.tx.instanciasRotina[lookup("dedupeKey", e.dedupeKey)].update({ dedupeKey, dataPrevista, competencia, tipoPrazo, status: STATUS_INICIAL, donoId, ...(dataPrevistaEstimada ? {dataPrevistaEstimada} : {}) }).link({ template: e.templateId })`.
   Use `.update()`, never `.create()` — a lookup sentinel is illegal on `create`
   (RESEARCH Pitfall 2, verified in the SDK source). Always include `donoId`: the
   lookup-update's create path is evaluated by `instant.perms.ts`'s `create` rule
   against `newData.donoId` and is rejected without it (RESEARCH Pitfall 6).
6. **Concurrency tolerance.** Wrap the transact in try/catch. On failure, re-query the
   `toCreate` dedupeKeys; if every one now exists, a concurrent run won the race —
   return them under `existing` and do not retry or throw. If any are still missing,
   rethrow. The authoritative non-duplication guarantee is the schema-level
   `dedupeKey.unique()` constraint, NOT the step-4 diff; the diff exists to protect
   `status`, and this step exists so the unique constraint's enforcement never surfaces
   as a broken app.
7. **No deletes, ever.** This function contains no `.delete()` call and no code path that
   could produce one, for any reason (ROADMAP success criterion 3).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (untrusted client) → InstantDB | The job runs entirely in the user's browser; there is no server tier. `instant.perms.ts` is the only enforcement point |
| job compute output → persisted records | Every computed `dedupeKey`/`dataPrevista` becomes durable state; a wrong key permanently duplicates |
| concurrent job runs (two tabs, or a tab + a CLI run) → same dedupeKey | Two writers may race on the same key with no coordination between them |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | `runRoutineInstanceJob` write payload | mitigate | Structural: an already-present dedupeKey is filtered out at step 4 and therefore never appears in any transact payload, so no code path can overwrite `status`. Proven by Task 3 steps 3-4 (set `concluida`, re-run, re-assert) — a count-only test would not catch this (RESEARCH Pitfall 1) |
| T-05-02 | Tampering | Concurrent runs racing on one dedupeKey | mitigate | Authoritative guarantee is `instanciasRotina.dedupeKey.unique()` in the pushed schema (re-verified in 05-01 Task 1), not the app-level diff. Step 6's catch-and-re-query converts a lost race into an `existing` report instead of a crash. Full concurrent-double-run proof is 05-06 Task 2 |
| T-05-03 | Elevation of Privilege | Upsert create path without `donoId` | mitigate | `donoId` from `db.getAuth()` is included in every payload; `instant.perms.ts`'s `create` rule (`auth.id == newData.donoId`) rejects otherwise. Task 3 asserts non-empty `donoId` on every written record |
| T-05-04 | Tampering | Accidental delete path | mitigate | Grep gate in Task 1 acceptance criteria asserts zero `.delete(` occurrences in `routineJob.ts`; Task 3 run-2 asserts the id set is unchanged, which fails if anything was deleted and recreated |
| T-05-19 | Denial of Service | Job failure breaking the SPA | mitigate | `onMount` handler is try/caught with a console log; rendering is unaffected. Task 2 acceptance criteria require the `console.error` path to exist |
| T-05-20 | Information Disclosure | Admin SDK leaking into the shipped bundle | mitigate | `@instantdb/admin` is imported only under `web/e2e/`; Task 2 and Task 3 acceptance criteria grep both `web/dist` and `web/src` for it |
| T-05-21 | Tampering | Timezone-local date computation shifting the range | mitigate | `today` computed with UTC getters only; grep gate forbids `getFullYear`/`getMonth()`/`getDate()` in `routineJob.ts` |
| T-05-22 | Tampering | Un-normalized `i.date()` round trip making every instance look new | mitigate | Mandatory `toIsoDate` normalization on every DB-sourced date, unit-tested in Task 1; Task 3's run-2 count assertion is the end-to-end detector |
| T-05-23 | Denial of Service | `$in: []` on an empty template set | mitigate | Step 1 short-circuits before the instance query; behavior of `$in: []` is deliberately never relied on (RESEARCH Open Question 2) |
</threat_model>
