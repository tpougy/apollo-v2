<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verification script → live InstantDB app | The script writes and deletes real records in the user's real app; there is no separate test database |
| verification script → credentials | The script touches the session file's permissions and must never read or print its contents |
| documentation → operator behavior | README instructions are what the operator will actually do with a long-lived credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-28 | Tampering | Verification script leaving junk records in the real controladoria app | mitigate | Every seeded record is cleaned up by a `trap`; a post-run assertion checks no test-prefixed record remains; idempotency proven by two consecutive green runs |
| T-03-29 | Information Disclosure | Script or README echoing the session file's contents | mitigate | Script only ever runs `stat` on the session file, never `cat`; README documents the path and the 0600 requirement without ever printing a token; grep gate in Task 2 checks for `0600` documentation, not for token values |
| T-03-30 | Elevation of Privilege | Verification passing while the admin token has crept into a data path | mitigate | The CLI-11 section runs both the AST confinement test and an independent grep, and the whole script fails if either produces output |
| T-03-31 | Repudiation | A green verification that never actually exercised the live app | mitigate | Every CRUD gate is a live pytest module with `0 skipped` required; a skip (which is what "no session" produces) fails the gate rather than passing it |
| T-03-32 | Spoofing | Verification re-sending magic codes on every run, desensitizing the operator to auth email | mitigate | CLI-01's gate asserts the persisted session works and that the plan-03-01 evidence file exists; it never triggers `send_magic_code` |
</threat_model>
