# Quick Task 260923-h35: Cloudflare Pages env-var fallback for InstantDB app_id Summary

**`web/vite.config.ts` now falls back to `process.env.VITE_INSTANT_APP_ID` when the gitignored `../.env.instantdb` file is absent, unblocking Cloudflare Pages builds while leaving local-dev file-based resolution byte-identical.**

## Performance

- **Duration:** ~10 min
- **Tasks:** 1/1 completed
- **Files modified:** 1

## Accomplishments
- `web/vite.config.ts` app-id resolution wrapped in an `existsSync(envPath)` check: true-branch is the exact pre-existing `parse(readFileSync(envPath))` logic (byte-identical for local dev); false-branch falls back to `process.env.VITE_INSTANT_APP_ID`.
- Throw-if-missing guard extended to name both sources (`${envPath}` file keys, or `VITE_INSTANT_APP_ID` in `process.env`) in its error message.
- `INSTANT_APP_ADMIN_TOKEN` handling completely unchanged — it stays reachable exclusively through the parsed-file branch; the new `else` branch is the only new `process.env` read in the file and reads only the app-id key.
- Live-proven via a full build matrix (see Deviations for the one script adjustment needed): file-present baseline, file-absent+env-var fallback (produces the identical app_id as the baseline), file-absent+no-env-var failure (fails with the expected error text), and a post-restore sanity build confirming `.env.instantdb` was byte-identically restored.

## Decisions Made
- Kept the fallback to a single explicit `process.env.VITE_INSTANT_APP_ID` read rather than Vite's `loadEnv`/`envPrefix`, per the plan's explicit constraint — the same source file holds `INSTANT_APP_ADMIN_TOKEN`, and broad env injection risks baking that credential into the browser bundle.
- Preserved the existing `if (!appId) { throw ... }` check's position (after both branches converge) rather than duplicating it per-branch, extending only its message text.
