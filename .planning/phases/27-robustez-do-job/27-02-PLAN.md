JOB-01: the `encadeado` successor's `dataPrevistaEstimada` decision currently compares `record.status !=
"concluida"` against one exact lowercase, unaccented literal — the real onboarding data recorded
"Concluída"/"CONCLUIDA" and the comparison silently missed every one of them, computing a stale estimate
flag. This plan replaces the exact comparison with `_is_concluida`, a normalized comparison
(trim + casefold + accent-strip) tolerant of BOTH the word's feminine (`concluida`) and masculine
(`concluido`) grammatical forms — CONTEXT.md's own three worked examples require recognizing both. `status`
itself is NOT validated or constrained at write time; this is a read-only comparison internal to the job
(REQUIREMENTS.md's explicit decision — normalize the comparison, never close the vocabulary).

JOB-03: diagnosing a `skipped` entry today requires cross-referencing `templateId` against a separate
`template listar` call. This plan adds the template's `nome` directly to every `skipped` entry, in both
runtimes — an additive JSON contract change requiring the same mechanical retrofit of every existing fixture
scenario (both languages already assert the `skipped` shape by exact equality).

Purpose: successor date estimation stops silently breaking on realistic status casing/accenting; diagnosing a
batch `gerar-instancias` run stops requiring a second CLI call to resolve a name.

both runtimes' `skipped` reporting, a corrected `instancia status` docstring, a fully-retrofitted shared
fixture (every scenario, including Plan 01's), and two new permanent live tests proving both requirements
against the production InstantDB app.
