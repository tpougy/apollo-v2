<objective>
Close the schema gap that blocks the entire phase: `templatesRotina` has no field
encoding WHICH day a `du_fixo`/`corrido_fixo` template targets, nor how far after
its antecessor an `encadeado` template falls. Add exactly one optional numeric
attribute, `offsetDias`, push it live, and make it settable from both channels so
the generation job built in plans 05-02..05-06 has real data to consume.

Purpose: without a live, user-settable `offsetDias`, the job in JOB-01/JOB-02 has
nothing to compute from and every template would be skipped. This is the tracer's
first step: schema live before any generation logic exists.
Output: `offsetDias` live in InstantDB, `--offset-dias` on the CLI, an `offsetDias`
number input on the SPA template screen, and regression proof that pre-existing
templates (which have no `offsetDias`) still work on both channels.
</objective>

## Design decisions locked by this plan (referenced by 05-02..05-06)

**D-05-A — single dual-purpose `offsetDias` field.** RESEARCH.md Assumption A1 and
its "Alternatives Considered" row both recommend ONE optional numeric field over
three type-specific fields, because a template has exactly one `tipoGeracao` at a
time and the existing schema has no precedent for type-conditional field families.
Interpretation per `tipoGeracao`:

| `tipoGeracao` | Meaning of `offsetDias` | Valid range |
|---------------|-------------------------|-------------|
| `du_fixo` | Nth **business** day of the month (ANBIMA calendar) | integer >= 1 |
| `corrido_fixo` | Nth **calendar** day of the month, clamped to the month's last day | integer >= 1 |
| `encadeado` | Number of **business** days after the antecessor instance's `dataPrevista` | integer >= 0 |

**D-05-B — encadeado offset counts BUSINESS days (RESEARCH Open Question 1 / A2, resolved here).**
RESEARCH.md flagged this as the one genuinely open question and recommended business
days as the default. This plan adopts that recommendation explicitly rather than
leaving it assumed: the whole domain is dias-úteis-centric (PROJECT.md C-03 vendors
the ANBIMA calendar precisely because business-day math is the domain's native unit),
`du_fixo` is business-day based, and `corrido_fixo` exists specifically as the opt-in
calendar-day escape hatch. An encadeado chain that silently counted calendar days
would land routine deadlines on weekends and ANBIMA holidays — the exact failure the
vendored calendar exists to prevent. **Decision: `encadeado` uses `addBusinessDays`.**
If a real-world template ever needs a calendar-day chain, that is a future schema
addition (a `tipoOffset` discriminator), not a silent reinterpretation of this field.

**D-05-C — no new field for `tipoPrazo`.** CONTEXT.md leaves generated-instance
`tipoPrazo` to the planner. Generated instances get the constant `"soft"` (defined
in 05-02 as `TIPO_PRAZO_GERADO`). Rationale: hard-deadline semantics are behavioral
and PROJECT.md C-09 defers every behavioral deadline rule out of this milestone;
labelling generated instances `"hard"` would advertise enforcement that does not
exist. This keeps the schema addition to exactly one attribute.
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → live InstantDB app | A schema push is an irreversible, app-wide structural change applied directly to the single production app (no staging app exists) |
| SPA form / CLI flag → `templatesRotina.offsetDias` | User-supplied numeric input crosses into a field the generation job will feed into date arithmetic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-09 | Tampering | `bun run instant:push` against `shared/instant.schema.ts` | mitigate | Additive-only change; Task 1 acceptance criteria re-pull the server schema and assert every pre-existing `templatesRotina` attribute plus `instanciasRotina.dedupeKey.unique()` survived |
| T-05-10 | Denial of Service | Pre-existing Phase 3/4 templates with no `offsetDias` | mitigate | Field is `.optional()` and `required: false` on both channels; Task 2/3 include explicit regression coverage that legacy templates still list and edit |
| T-05-11 | Tampering | CLI `editar` default value | mitigate | `--offset-dias` defaults to `None` and flows through `drop_none`, so an unrelated edit can never silently reset a configured offset |
| T-05-12 | Information Disclosure | `offsetDias` written without `donoId` | accept | `create_entity`/`update_entity` (CLI) and `EntityScreen.svelte` (SPA) already inject `donoId` from the authenticated session; this task adds no new write path, and `instant.perms.ts` rejects any transact whose `newData.donoId != auth.id` server-side |
| T-05-13 | Elevation of Privilege | Range validation of `offsetDias` deferred to the job | accept | An out-of-range offset produces a skipped template with a machine-readable reason (05-02), never a crash or an out-of-range date; validating at write time would diverge between the two channels and give a false sense of enforcement |
</threat_model>
