<objective>
Build the shared `SubtarefasPanel.svelte` component and `TicketsSection.svelte`, and wire the
first (riskiest, previously-unproven) end-to-end path of NEST-05: selecting a ticket opens an
inline, non-Sheet panel scoped to that ticket's subtarefas, and creating a subtarefa from the
panel pre-resolves the `xorLink` parent by driving the generic engine's own DOM — without the
user ever touching `xor-parent-type`/`link-ticket` themselves.

Purpose: `20-RESEARCH.md`'s central finding is that `presetLinks` does NOT pre-resolve
`subtarefas`' `xorLink` on create (`EntityScreen.svelte:212-219` only merges `presetLinks` into
`config.links`, and `subtarefas.ts` has no `links`, only `xorLink`). This plan proves the
DOM-driving workaround (Pattern 1) live against the hosted app for one full parent-type path
before Plan 03 reuses the exact same component for the tarefa-parented path.
Output: `SubtarefasPanel.svelte` (shared, parent-type-agnostic), `TicketsSection.svelte`, Shell
routing, and a passing e2e spec proving the driven-create flow.
</objective>

`ProjetosSection.svelte:185-197`'s `openProjetoDialog` already uses (`Date.now()`-deadline loop,

`hostEl.querySelector('[data-testid="entity-create-start"]')`, click it — this opens the create

behavior `ProjetosSection.svelte`'s own comments document); (2) poll `document.querySelector` (NOT
`hostEl`-scoped from here on, since the Dialog now lives outside the hidden div) for
`[data-testid="xor-parent-type"]`, click it; (3) poll `document.querySelectorAll('[role="option"]')`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (Svelte SPA) → InstantDB | `scopeWhere`/`presetLinks` shape the client's own query/transact payload; the real authorization boundary is `instant.perms.ts` (unchanged, out of scope this milestone), which already scopes every query/transact to the authenticated `donoId` independent of any client-supplied filter. |
| Same-origin DOM (SubtarefasPanel's own driven-click code) → EntityScreen's rendered form | Not a security boundary — app code driving its own already-rendered, same-origin DOM, no cross-origin or privilege change involved. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-01 | Elevation of Privilege | `SubtarefasPanel.svelte`'s `scopeWhere`/`presetLinks` usage | low | mitigate | Code comment in `SubtarefasPanel.svelte` states explicitly that `scopeWhere`/`presetLinks` are client-side UI filters, not an authorization mechanism — the real boundary is `instant.perms.ts`'s unchanged `donoId` scoping (verified in `20-RESEARCH.md` Security Domain), preventing a future maintainer from assuming the panel is itself a security control. |
| T-20-02 | Tampering | `SubtarefasPanel.svelte`'s cloned `EntityConfig` | medium | mitigate | Always `{ ...subtarefasConfig, capabilities: {...} }` spread-clone, never mutate the shared `configByEtype("subtarefas")` object in place — `configByEtype` returns the same reference to every caller (`registry.ts:35-37`), so an in-place mutation would silently disable "novo" everywhere else `subtarefasConfig` is used, not just inside this panel. |
| T-20-03 | Denial of Service (client-local) | `SubtarefasPanel.svelte`'s driven-create poll sequence | low | accept | If a poll step times out (e.g. bits-ui's option list renders one reactive tick later than assumed), the function throws rather than hanging silently; worst case is a failed create attempt with a visible error, no data-integrity risk — `EntityScreen.svelte`'s own submit-time xorLink guard (`EntityScreen.svelte:277-281`, unchanged) still blocks any submit with an unresolved parent regardless of how the fields got that way. |
