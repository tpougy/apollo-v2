Output: A real second-user session isolated from tp@'s, a live-marked pytest module proving create/update/delete denial, and a guarded teardown that removes the second user without endangering tp@.

<scope_notes>
**Isolation proof must be WRITE-based, never query-based.** `cli/tests/test_auth_rejection.py` test 6 already documents (as executable documentation) that InstantDB's `view` rule silently filters disallowed rows out of query results: an empty `listar` returns HTTP 200 with `[]` whether or not perms are enforced, and whether or not any matching row exists. A VERIFY-05 assertion of the form "the second user's `apollo fundo listar` shows nothing" is worthless. Only `pytest.raises(InstantAPIError)` with `body["type"] == "permission-denied"` on a **create / update / delete** attempt is valid evidence. The requirement's word "view" is satisfied by the fact that the same `donoRules` `view` expression is the one the `update`/`delete` rules use, plus the update/delete denial proving the row is genuinely unreachable — state this explicitly in the module docstring rather than faking a view assertion.
</scope_notes>
