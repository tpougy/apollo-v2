<objective>
Build `apollo import --from-json <arquivo>` (plus `--dry-run`): a single, cross-entity command that
bulk-creates `fundos` + `templatesRotina` from one JSON file, with cross-entity/cross-record
references resolved via a `_local_id` + `$`-prefix convention, full two-pass validation collecting
ALL errors before any write, natural-key idempotency (no schema `unique()` needed), client-side id
pre-assignment so every reference resolves to a real id before any transact chunk is built, and ONE
atomic `client.transact()` covering the whole batch's new-only records.

This is the phase's Wave 1 (foundation) plan and carries the phase's own tracer task: Task 1 wires
every layer of the new command — file parse, both validation passes, existence-check queries,
id resolution, the heterogeneous atomic transact with `routine_job.py`'s own live-proven
ambiguous-failure recovery, and the CLI surface — end-to-end, live-proven against the real
production InstantDB app at a meaningful scale (multiple fundos + multiple templates, including an
encadeado chain and both reference forms), not 1-2 trivial records. Task 2 expands validation rigor
(multi-error collection, `--dry-run`, same-file re-run idempotency) without touching production code
again. Plan 31-02 (Wave 2) proves the command at the full literal 18-fundo/84-template onboarding
scale (ROADMAP Success Criterion 3) and the partial-failure-resume scenario.

call's output, with no way to resume after a mid-batch failure without risking duplicates (neither

Output: `apollo import --from-json <arquivo> [--dry-run]`, live-proven end-to-end; `batch_import.py`

## D-NN decision-ID mapping (31-CONTEXT.md's `<decisions>` block uses plain numbers 1-10, not a
"D-NN" prefix — this plan assigns the mapping below once, for citation traceability; both forms
refer to the SAME locked decisions)

- D-01 = decision 1: single cross-entity `apollo import --from-json <arquivo>` command (not one
  command per entity) — SC1 needs cross-entity references in one file, SC3 needs one invocation.
- D-02 = decision 2: file shape is one top-level JSON object with `fundos`/`templatesRotina` keys
  only; each record's fields mirror the EXACT `--flag` names already accepted by
  `fundo criar`/`rotina template criar`, reusing the SAME validation constants
  (`REGRAS_COMPETENCIA_SUPORTADAS`, and the two constants this plan promotes) — no new validation
  vocabulary invented.
- D-03 = decision 3: every record carries a required `_local_id` (unique across the WHOLE file, both
  entity lists combined); `fundoId`/`antecessorId` accept either a real pre-existing InstantDB id
  (bare string) or `"$<local_id>"` (same-batch reference); `antecessorId` may chain to another
  same-batch template (encadeado chains).
- D-04 = decision 4: full validation BEFORE any write, two pure (zero-write) passes — forma (required
  fields/types/choices) then referências (every `$<local_id>` resolves, right entity type, no
  antecessor cycle) — collecting EVERY error across BOTH passes, never fail-fast; any error anywhere
  → complete error list, exit 2, zero writes for the whole file.
- D-05 = decision 5: idempotency by natural key, not a schema `unique()` constraint (neither entity
  has one) — `fundos`: `(donoId, codigo)`; `templatesRotina`: `(donoId, resolvedFundoId, nome)`
  (`resolvedFundoId` may be `None` — a valid key component, not an error). A matching existing row is
  reported `existing`, never recreated, never an error.
- D-06 = decision 6: id resolution happens BEFORE any transact — `new_id()` client-side pre-assignment
  (generalizing `crud_helpers.create_entity`'s single-record idiom to N heterogeneous records) so
  every `$`-reference, including one same-batch new record pointing at another same-batch new record,
  resolves to a real id regardless of file order — no topological sort needed.
- D-07 = decision 7: ONE atomic `client.transact(chunks)` for the whole batch's NEW-only records
  (fundos + templates together, `existing` records never enter the payload) — mirrors
  `routine_job.py:947-957`'s live-proven heterogeneous-chunk pattern. On an ambiguous
  post-send network failure, re-query by natural key exactly like `routine_job.py:955-970`; report
  landed records as `existing`, only re-raise if the recheck confirms nothing landed.
- D-08 = decision 8: report shape mirrors `gerar-instancias`'s `{created, existing}` pattern, per
  entity: `{"fundos": {"created": [...], "existing": [...]}, "templatesRotina": {"created": [...],
  "existing": [...]}}` on success — lists of `_local_id`s (not real InstantDB ids), for human
  traceability against what the operator wrote. `{"errors": [...]}` on validation failure (no
  `fundos`/`templatesRotina` keys — nothing was processed).
- D-09 = decision 9: `--dry-run` mirrors `gerar-instancias --dry-run`'s existing flag — runs full
  validation + existence-check + id resolution, never calls `transact`, returns the same report shape
  labeled as what WOULD happen.
- D-10 = decision 10: scope is ONLY `fundos` + `templatesRotina` — no other entity, and `instanciasRotina`
  in particular is NEVER created by this command (PROJECT.md C-06 continues to hold: only
  `gerar-instancias` creates instances).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator-supplied `--from-json <arquivo>` JSON file → parsed batch data → InstantDB writes | The file is authored by the same authenticated local operator (not a remote/network-facing input), but is parsed as structured, partially-trusted data before ever reaching a write path — a malformed or adversarially-shaped file must never crash uncontrolled, silently forge ownership, or reach a code path capable of creating an `instanciasRotina` row. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-01 | Tampering | batch_import.py's fundo/template form validation | medium | mitigate | Any record carrying a `donoId` key is rejected at validation time before any query/write — defense-in-depth on top of C-05's server-side `create: auth.id == newData.donoId` perms rule, which independently blocks the same forgery attempt. |
| T-31-02 | Tampering | run_batch_import's file read/parse step | medium | mitigate | `json.JSONDecodeError`/`UnicodeDecodeError` are caught explicitly and folded into the same `{"errors": [...]}`/exit-2 contract — never an uncaught traceback. |
| T-31-03 | Elevation of Privilege | reference-validation's bare/real-id branch | high | mitigate | Every non-`$` `fundoId`/`antecessorId` is existence-checked via `get_entity` before being trusted, mirroring `_resolve_ref`'s single-record precedent; InstantDB's own per-op perms rule is a second, independent barrier against linking to another user's record. |
| T-31-04 | Repudiation | run_batch_import's post-transact-failure recovery | high | mitigate | On any `(InstantAPIError, httpx.HTTPError)`, every attempted natural key is re-queried before reporting failure — a record that actually landed is never reported as failed (which would otherwise prompt a duplicate-creating retry); mirrors `routine_job.py`'s own live-proven recovery path. |
| T-31-05 | Tampering | batch_import.py's top-level key validation | critical | mitigate | Only the two supported entity keys are accepted at the top level (any other key is rejected); the module defines no constant referencing the instance entity type at all — structurally incapable of writing one, live-proven by this plan's own before/after row-count-unchanged assertion (C-06). |
| T-31-06 | Denial of Service | run_batch_import reading/holding an arbitrarily large file in memory | low | accept | Single-user local CLI; the operator already has filesystem-level access to any file they point `--from-json` at — same trust boundary as every other CLI argument in this codebase, no pagination/streaming needed at this scale (mirrors Phase 30's T-30-05 acceptance rationale). |
| T-31-07 | Information Disclosure | error report echoes user-supplied field values back in `{"errors": [...]}` | low | accept | The operator already authored every value in their own local file; no cross-user data ever crosses this boundary. |
